# supergrep v0.1 검증 리뷰 — 2026-09-23

## 결론

현재 구현의 실제 모델 실행, 패키지의 런타임 로딩, 간단한 fixture의 byte/line 좌표와 네트워크 syscall 미발생은 재현했다. 일반 테스트와 lint도 통과한다. 그러나 **“성능 목표 처리만 남았다”는 결론에는 동의하지 않는다.** 기본 fast 후보 선택의 경로 편향, 해당 경로를 실행하지 않은 품질 평가, 한국어 코드 검색 수치 오표기가 남아 있다.

검토 과정에서는 제품 코드, 기존 평가 label, 모델/성능 설정을 변경하지 않았다. 이 리뷰 문서만 추가했다. 아래 실행 증거는 별도의 `/tmp/supergrep-review-*` 파일에 저장했다.

## 발견 사항

### F1 · P1 — fast 후보 축소를 검증하지 않고 품질 통과로 처리함

- 위치: `docs/progress.md:169`, `docs/model-decision.md:124`, `examples/evaluate.rs:277`.
- holdout 원본의 모든 질의에서 corpus와 후보 수가 모두 40이다. 기본 K=128보다 작으므로 실제로 후보를 줄이지 않는다. evaluator는 이 경우 fast 결과를 복제해 deep 결과를 만든다. 전체 집합을 평가한 결과를 재사용하는 동작 자체는 합리적이지만, 이 실행으로 fast의 후보 선별 품질을 검증할 수는 없다.
- 보고된 영어 candidate recall 0.90은 128개로 줄일 때의 정답 회수율이 아니다. 전체 40개를 다 넣은 상태에서도 gold evidence의 절반을 덮는 청크가 없는 사례 때문에 낮아진 값이다.
- README와 진행 기록에 이 한계를 언급했지만, S5의 “품질 목표 통과”와 “남은 결정은 성능뿐”이라는 결론은 그 한계와 맞지 않는다.
- 조치: N이 K보다 충분히 큰 별도 평가 corpus에서 fast 선택 경로를 실행하고 후보 evidence recall, fast/deep 최종 품질 차이를 측정한다. 기존 holdout label을 결과에 맞춰 고치지 말고, 최소 근거 span 및 평가 가능한 gold coverage를 사전 점검한 추가 benchmark를 버전으로 구분한다.

### F2 · P2 — 분산 후보가 경로 앞부분으로만 편중됨

- 위치: `src/search.rs:369–389`.
- source를 경로순 BTreeMap으로 순회하고, 첫 순회에서 파일마다 하나씩 청크를 꺼낸다. 후보 budget만큼 앞에서 잘라 쓰므로 lexical 근거가 없고 파일 수가 K보다 많으면 사전순 첫 K개 파일만 선택한다. 후반 경로는 분산 표본에서도 빠진다.
- 실제 packaged binary와 기본 모델로 재현했다. 144개의 짧은 영문 distractor 파일 `a000.rs`–`a143.rs`와 정답 `z-target.rs`, 한국어 질의 “요청 실패 후 재시도 대기 시간을 늘리는 부분”을 사용했다.

| 실행 | 전체 청크 | 평가 청크 | lexical 근거 | 정답 |
| --- | ---: | ---: | --- | --- |
| 기본 fast | 145 | 128 | 없음 | 후보에서 누락. 선택 경로는 `a000.rs`–`a127.rs` |
| deep | 145 | 145 | 없음 | `z-target.rs`가 1위 |

- 검증 때 `--top-k 200`으로 평가한 모든 파일이 결과에 나타나게 했다. 정답 부재가 화면의 top-k 제한 때문이 아님을 확인했다. 이 사례는 대규모 recall 추정치가 아니라 선택 정책의 구조적 경로 편향 재현이다.
- 조치: 파일 경로 목록 전체에 걸쳐 결정적으로 표본을 분산시킨 뒤 파일 내부 위치를 분산한다. 후보 밖의 정답을 항상 찾을 수 있다는 보장은 할 수 없지만, 파일명 순서만으로 후반 경로 전체를 제외하는 편향은 제거할 수 있다. K보다 파일 수가 많은 zero-overlap 회귀 사례를 추가한다.
- 증거: `/tmp/supergrep-review-selection-acyss315/{summary.json,fast.json,deep.json}`.

### F3 · P2 — 한국어→영문 코드 Hit@5를 잘못 집계하여 보고함

- 위치: `docs/progress.md:178`, `docs/model-decision.md:121`.
- 0.85는 한국어 전체 20개 질의의 수치다. 코드 외 설정·문서·로그 질의도 포함한다.
- 같은 원본에서 `mode=deep`, `language=ko`, `category=code`로 집계하면 **10개 중 7개 적중, Hit@5=0.70**이다. `holdout-code-03-ko`, `holdout-code-05-ko`, `holdout-code-10-ko`가 실패한다.
- 따라서 “한국어→영문 코드 0.85”는 고쳐야 한다. 언어 전체 목표와 코드 하위집합 목표를 분리하고, 각 표의 분모/필터를 명시한다. 현재 전체 언어 Hit@5 0.85 자체는 원본 재집계로 재현된다.

### F4 · P2 — 성능 검증이 계획의 질의 다양성을 충족하지 못함

- 위치: `scripts/benchmark.py:39–45`, `scripts/generate_benchmark_corpus.py:20–32`.
- 21 fresh-process 실행 모두 동일한 영어 질의 하나를 사용한다. corpus 역시 retry 함수 템플릿의 반복이다. 계획은 첫 실행과 별도로 서로 다른 질의 최소 20회의 실행 시간을 요구했다.
- 25.6867초 median / 26.4187초 p95는 저장된 raw run과 일치한다. 다만 이는 같은 합성 workload의 반복 측정이며, 질의 길이·언어·선택되는 청크가 달라질 때의 사용성을 대표하지 않는다.
- 조치: 기존 값은 단일 workload 기준으로 유지한다. 개발용 고정 질의 목록을 입력으로 받아 영어·한국어 및 여러 길이를 포함해 측정하고, binary/model/corpus 식별자와 실행 환경을 함께 기록한다. 이 검증을 완료한 뒤 latency 목표 수용 여부를 결정한다.

### F5 · P2 — benchmark가 큰 stdout/stderr에서 멈출 수 있음

- 위치: `scripts/benchmark.py:55–62`.
- stdout/stderr를 PIPE로 열고 자식이 종료될 때까지 `poll()`만 한다. `communicate()`는 자식 종료 뒤에 호출한다. 결과 JSON 또는 진단이 pipe 용량을 넘으면 자식은 쓰기에서, 부모는 종료 대기에서 멈춘다. timeout도 없다.
- 임시 fake CLI가 stdout 8MiB를 쓰는 경우, 단독 `subprocess.run(capture_output=True)`는 정상 종료하지만 `run_once`를 통한 실행은 3초 뒤에도 완료되지 않았다. 해당 임시 테스트 process group만 종료했다.
- 기존 21회 측정이 틀렸다는 의미는 아니다. 추후 corpus/진단을 확장하면 성능 측정 자체가 완료되지 않을 수 있다는 문제다.
- 조치: 자식 실행 중 출력을 지속적으로 읽거나 임시 파일로 redirect하고, 별도의 RSS sampling과 timeout을 둔다. 큰 JSON/진단을 반환하는 CLI를 회귀 테스트에 포함한다.
- 증거: `/tmp/supergrep-review-pipe.txt`.

## 권장 처리 순서

먼저 후보 선택과 검증 도구를 수정하고, 코드 검색 수치를 정정한 뒤 큰 corpus의 후보 회수율과 여러 질의의 latency를 검증한다. 그 결과를 보고 15초/10초 목표를 유지할지 변경할지 결정하는 것이 맞다. 현 시점에는 latency 목표만 완화하여 v0.1 전체 완료로 처리하지 않는 것을 권한다.

## 후속 검증 결과 (같은 날짜)

- **F1:** 28개 원본 파일과 결정적 무관 파일 240개를 결합한 280청크
  감도 검사에서 K=128 후보 축소를 실제로 실행했다. 영어 fast/deep
  Hit@5는 0.85/0.85였지만 한국어는 0.50/0.85였다. 한국어의 표현 가능한
  gold에 대한 후보 회수율은 0.56이다. 후보 누락 문제가 확인되었으므로
  F1을 단순 통과로 닫지 않는다. 원시 기록과 집계:
  `artifacts/evaluation/compact-multilingual-scale-v2-holdout*`.
- **F2:** 경로 양끝과 중간을 반복적으로 선택하는 결정적 표본 순서를
  구현했다. 145파일 회귀 테스트와 수정된 release binary의 실제 모델
  검색에서 `z-target.rs`가 128개 후보에 포함되고 1위로 반환됐다.
  증거: `/tmp/supergrep-review-selection-acyss315/fast-fixed.json`.
- **F3:** README, `docs/model-decision.md`, `docs/progress.md`에서
  한국어→영문 코드 Hit@5를 0.70(7/10)으로 고쳤다. 영어/한국어 전체
  언어 slice의 0.85와 분리했다. 평가기에 gold 표현 가능성과 조건부
  후보 회수율도 추가했다.
- **F4:** 21개 서로 다른 영어·한국어 development 질의를 각 fresh

- **F5:** stdout/stderr를 임시 파일로 받아 pipe 정체를 없애고 timeout을
  추가했다. 8 MiB stdout을 쓰는 가짜 CLI 회귀 테스트가 통과했다.
- 전체 Rust 테스트 79개 통과, 1개 opt-in 제외; format/lint 및 Python
  회귀 테스트 통과. 새 release bundle의 실제 모델 검색, 정확한 byte/line
  범위 및 network syscall 부재도 통과했다. 새 tarball은
  `artifacts/packages-reviewed/supergrep-v0.1.0-linux-aarch64.tar.gz`.

이 후속 결과로 “남은 결정은 지연뿐”이라는 앞선 상태 판단은 여전히
성립하지 않는다. 한국어 fast 후보 회수율 문제와 두 지연 목표 미달을
각각 처리해야 한다. 확장 감도 검사는 검토한 holdout label을 재사용했으며
새로운 blind holdout으로 취급하지 않는다.
